# Known limitations

Written before the code. It will be updated as the build finds more.

- **Mezo governance risk.** All Mezo core contracts are upgradeable proxies. A hostile or accidental upgrade can break or lock Trozu positions. Trozu has no way to prevent it. See THREAT_MODEL T14.
- **Oracle risk is inherited.** The price comes from a chain precompile through `PriceFeed`. Trozu adds no oracle of its own.
- **Redemption buffer is an estimate.** It is exact only for a complete walk at one block, and it moves. Sort order uses NICR, which ignores interest and pending redistribution. A capped walk gives only a lower bound.
- **Wave 1 has no marketplace.** A wave 1 NFT sale is trust-based: the seller can change the position before the buyer's transfer lands. State-committed settlement is wave 2.
- **Wave 1 has no guardian.** Wave 1 vaults cannot be acted on by anyone but the holder. The guardian needs a vault v2 and a new factory, so wave 1 positions do not get it unless migrated.
- **A holder that cannot receive BTC cannot close or withdraw.** Payouts go to the caller. A contract holder without a payable `receive` reverts its own operations.
- **Test MUSD is scarce.** There is no MUSD faucet. Opening a trove costs at least 1800 MUSD net debt.
- **Local tests use the pinned MUSD source, not the live contracts.** The pinned commit can differ from what runs on matsnet. The final fork layer checks the live proxies, and the proxy implementations are not verified yet.
- **Not audited.** Mezo requires a third-party audit for Mezo Market featuring. This repository has not had one.
- **Recovery Mode and the last trove.** While the system is in Recovery Mode, refinance and close revert, and collateral cannot be withdrawn. The last trove in the system cannot close. These are Mezo rules, shown in the Lens as `recoveryMode` and `canClose`. See THREAT_MODEL T19.
- **`tokenURI` is empty in wave 1.**
- **Closing needs more MUSD than a position minted.** The opener receives the debt amount but owes the borrowing fee, interest and nothing for the 200 MUSD reserve. A holder must acquire a little extra MUSD to close.
- **Redemption defense needs the position near the queue front.** The walk is at most 100 troves. Further away the guardian's verdict is unknown and it never acts. See DECISIONS 44.
- **A close cannot use a permit.** The exact cost of a close changes every second with interest, so the app approves slightly more than the cost and then resets the approval to zero after the close (DECISIONS 43). The close flow has not been run end to end through the UI on testnet, because it needs about 0.029 BTC for a second position; the reset step is covered by review, not by a live run.
- **No screen reopens a closed trove.** A closed position keeps its NFT and vault for claim and sweep; opening again is a new position.
- **Mezo's gas estimation is unreliable.** The app and the keeper send explicit gas limits (DECISIONS 42) instead of trusting `eth_estimateGas`. A wallet that does estimate on its own can still fail on this network. Mezo also charges at least half of the gas limit, so the limits are a cheap ceiling and not free (6M costs under 0.000000001 BTC).
- **In the Wave 2 proof run the seller is also the fee recipient.** The market fee therefore goes from the buyer to the same address that is paid as seller, so the fee cannot be seen as a balance change. The evidence is the MUSD `Transfer` logs and the market's `Sold` event, which show both legs.
- **Minimum debt blocks small repayments.** Mezo keeps a trove's composite debt at or above 2,000 MUSD, so a position near the minimum can repay only the difference (1.83 MUSD on the proof position) until it closes.
- **Known npm advisories in `packages/`.** `npm audit` reports seven findings after the non-breaking upgrades (checked 2026-11-07). One is in production code: `zod` 3.25.76 (high, GHSA-mrhx-c7xc-m3w5, memory exhaustion when a very large array reaches an array schema). Trozu's own MCP input schemas hold no arrays (a test fails if one is added), but the MCP SDK validates protocol messages with its own zod schemas that do, so a client that sends an enormous array in a message such as `initialize` could crash the MCP server process. That client is the stdio peer the user started; there is no network listener and nothing to lose but the process. Planned fix, not done or scheduled: move `packages/mcp` to zod 4.6.6 or later, which needs a schema migration. The other six are development tooling only (vitest 2.1.9 with vite 5, esbuild 0.21, tinypool, vite-node, @vitest/mocker), about servers and options that `vitest run` does not use; the suggested fix is vitest 5, a major upgrade, also not done. Details in `packages/mcp/README.md`.
- **The SDK's gas limits have no measurement behind them for nine actions.** `repay`, `refinance`, `close`, `closeWithPermit`, `claimSurplus`, `fundReserveMusd`, `clearPolicy`, `cancelAll` and `setApprovalForAll` only have the floor (6M for calls that re-sort the trove, 1M for the rest) because none of them was ever sent on chain. The limits that do have evidence come from `docs/proof.json` or the wallet round trip, where every receipt shows exactly half the limit (the half-limit charge), so those prove a limit is enough, not what the call uses. Listed in `docs/INTEGRATIONS.md`.
